# Little Lobster Cafe & Bistro — website

Bilingual (TH served, EN switch) static site for **Little Lobster**, a chef-run Italian–French
bistro in a converted house at 34 Soi Prachachuen 9, Tha Sai, Nonthaburi. Built 3 Sep 2026
to the *Opus 5 Restaurant Master Prompt*, entirely from the restaurant's own public
channels — nothing about the business is invented, and every fact traces to
`design-system/SOURCES.md`.

Static HTML/CSS/JS. No framework, no build step for the pages themselves (a small Python
script renders the menu and pictures from data). Open `index.html` on any static host.

---

## This repository

Public. Three consequences worth knowing before you edit anything:

- **`_reference/` is not in it.** Those 66 files are other people's photographs — Lemon8
  and TikTok creators, RestaurantGuru uploads, press screenshots — used to research the
  site and never published. They stay on the designer's machine; `.gitignore` keeps them
  out. `design-system/SOURCES.md` still documents every one of them, so the provenance
  trail survives even though the images do not.
- **`_build/` is not in it either.** The two single-file builds are ~5 MB each of
  base64-embedded AVIF and are regenerable in one command, so committing them would add
  that to history on every rebuild. Run `python3 _source/make-artifact.py` when you want one.
- **The booking token is a placeholder.** `content/site.json → booking.token` and
  `_source/booking-sheet.gs` both read `CHANGE-ME-BEFORE-DEPLOYING`. A shared secret in a
  public repository is not a secret, so the real phrase is chosen at deploy time and lives
  only in the restaurant's own Apps Script and their own copy of `site.json`. See
  *Sending bookings to a Google Sheet* below.

**Rights.** The HTML, CSS, JavaScript, build scripts and design system are the studio's
work. The name, logo, photography and menu are Little Lobster's, used to build their own
site — they are not licensed for reuse. No licence file is included, so everything here is
all-rights-reserved by default. Read it, learn from it; do not redeploy it as a restaurant.

## Run it locally

macOS TCC blocks processes spawned by an app from reading `~/Downloads`, so copy the
folder to a scratch directory and serve from there:

```bash
rsync -a --exclude '_source' --exclude '_real' --exclude '_reference' "$PWD/" /tmp/ll-site/
python3 -c "import functools,http.server,socketserver;H=functools.partial(http.server.SimpleHTTPRequestHandler,directory='/tmp/ll-site');socketserver.TCPServer(('127.0.0.1',4517),H).serve_forever()"
```

QA query hooks on every page: `?static=1` (no motion, reveals shown), `&flat=1`
(fixed hero height for full-page capture), `&shift=N` (hide fixed chrome and offset),
`&touch=1` (behave as a touch device — mobile menu spotlight), `&lang=en`.

## Regenerating

```bash
python3 _source/media.py          # img/ from _real/  (needs CROP_TOOL=<path to the crop binary> for the crops)
python3 _source/build.py          # renders menu, chips, lunch card, gallery, marquee, symbols, partials into the pages (idempotent)
python3 _source/make-artifact.py  # the single-file build
```

Edit `content/menu.json` or `content/site.json`, run `build.py`, done. The pages carry
`<!--#name-->…<!--/name-->` markers; only what is between them is regenerated.

## The curtain

Every moment the whole screen is replaced — switching TH/EN, and moving between pages —
is covered by the same thing: the restaurant's **round sign**, the white disc with the
LITTLE LOBSTER lockup, on the plaster-green ground, carried up across the screen. It is the
same disc the loader lights up, so arriving and moving around feel like one system.

- It rises from below (380ms), the content changes while nothing can be seen (110ms), then
  it continues up and away (420ms).
- A page change hands over through `sessionStorage`: the outgoing page raises it, the
  incoming page starts covered and lifts, so the two halves read as one movement.
- Navigation fires at 400ms with a 1,200ms failsafe, so a slow page can never leave someone
  stuck behind it.
- Same-page anchors, the menu category rail and external links are deliberately excluded —
  nothing is being replaced there, so nothing is covered.
- Under reduced motion, or with JavaScript off, there is no curtain at all and the change
  is instant.

To change its timing, edit `C_IN` / `C_HOLD` / `C_OUT` in `js/ll.js` **and** the matching
durations in section 6 of `css/ll.css`; they are commented as a pair.

## The reviews page, and why it is built the way it is

The restaurant's rating is the most persuasive thing it has and the easiest thing on a
website to fake, so the page is built to be checkable:

- **The aggregate and the full distribution are Google's own numbers** — 4.7 from 129, and
  98/22/8/1/0 across five stars down to one. The one-star row is shown even though it is
  zero. The distribution sums to 129 and matches the average, so a reader can check it.
- **The page quotes the five-star reviews only** — the restaurant's choice, made on
  4 Sep 2026. It stays honest because the curation is stated on the page and the star
  distribution beside it still counts every four-, three- and two-star review. To put them
  back they would have to be re-harvested: `content/reviews.json → excluded` records that
  four sub-five-star reviews were dropped and why, but neither their text nor their
  authors' names — this repository is public and those four people did not ask to be
  listed as the ones who were left out. Each review shown is quoted in full, in the language
  it was written in. The one place a line *is* cut — a mention of a buffet the restaurant
  no longer runs — says so on the card.
- **Filter chips are built from the reviews themselves** and a chip that matches nothing is
  never rendered. `ห้าดาว / Five stars` is there for anyone who only wants the glowing ones.
- **Avatars are monograms**, never a copied Google profile picture. Where a review names a
  dish the restaurant has photographed, that photograph appears, captioned as the
  restaurant's own.
- **No `Review` or `aggregateRating` JSON-LD.** These reviews are not the venue's property.

An earlier harvest produced twenty reviews that an adversarial check found had been
*completed* past a truncated snippet. All twenty were thrown away. See `SOURCES.md` §J.

## The booking page, and what it deliberately does not do

Little Lobster has no reservation platform — not on eatigo, Chope, TableCheck, HungryHub or
Quandoo — and takes bookings itself on LINE and by phone. So `book.html` is a **request
composer**, not a booking engine with a fake backend:

- It asks for date, time, party size, name and phone, validates them, and writes the
  message.
- **The date is a full month calendar** — every day of every future month, not a handful of
  shortcuts. Arrow keys move a day, up and down a week, PageUp and PageDown a month, Home
  and End the week, Enter picks. Past days are disabled and today is ringed in red. Thai
  shows Buddhist years and the abbreviations a Thai calendar prints; the month, the weekday
  heads and the spoken labels all rebuild when the language switches. A native date field
  sits underneath for anyone who would rather type, and the two stay in sync.
- **The time buttons are the opening window**, generated from `content/site.json → hours`.
  They are labelled as opening hours, and nothing is ever drawn as an available slot,
  because no system here knows which tables are free.
- **No state says booked, confirmed or reserved**, whichever route the request takes.

### Sending bookings to a Google Sheet

The site is static and has no server, so a request goes straight from the guest's browser
into a sheet on **the restaurant's own Google account**. Nothing passes through the studio
or any third party. Until it is set up, the button does not appear at all and the form
falls back to composing a LINE message — it never pretends to have sent anything.

To turn it on, once, about ten minutes:

1. Make a Google Sheet on the restaurant's account and name the first tab `Bookings`.
2. **Extensions ▸ Apps Script**, delete the placeholder, paste in `_source/booking-sheet.gs`.
3. Change `TOKEN` at the top to a phrase of your own. Optionally put an address in `NOTIFY`
   to get an email for every booking.
4. Run `selfTest` once from the editor. It creates the headers and writes one test row —
   delete that row afterwards.
5. **Deploy ▸ New deployment ▸ Web app**, *Execute as: Me*, *Who has access: Anyone*. Google
   warns that anyone can call it; that is what lets a website form reach it, and the token
   plus the checks in the script are what limit what it accepts.
6. Put the `/exec` URL into `content/site.json → booking.endpoint` and the same phrase into
   `booking.token`, run `python3 _source/build.py`, and re-upload.

Editing the script later needs **Deploy ▸ Manage deployments ▸ Edit ▸ New version**, or the
old code keeps running.

What the sheet receives: date, time, party size, name, phone, note, the language the guest
was reading in, and the time it was sent. There is deliberately no column holding the
composed message — it was a second copy of the same personal details, so an erasure request
would have needed two places cleared. The privacy paragraph on the page lists exactly
that, in both languages, and swaps automatically depending on whether an endpoint is
configured — **if you change the payload, change that paragraph too.**

What the script defends against: a wrong or missing token, malformed dates, times, phone
numbers and party sizes, oversized fields, more than twenty rows in five minutes, and
**spreadsheet formula injection** — a guest whose name is `=IMPORTXML(...)` would otherwise
have it run the moment the owner opens the sheet, so leading `=`, `+`, `-` and `@` are
neutralised. What it cannot defend against, because the URL ships in public JavaScript, is
someone determined posting junk rows; if that ever happens, rotate the token in both files
and redeploy. The endpoint and token are emitted on `book.html` only, not on the other six
pages. For the retention line on the page to stay true, add `purgeOld` as a monthly
time-driven trigger in the Apps Script editor — it deletes rows older than `KEEP_DAYS`.

If the restaurant later adopts a real booking platform, replace the send block in
`js/ll.js` with that platform's widget and delete the composer — the rest of the page stands.

## The four things you will actually want to change

1. **Prices.** They are the LINE MAN delivery prices read on 3 Sep 2026 and are labelled as
   such on every page. When the restaurant confirms dine-in prices, set them in
   `content/menu.json` (add `price` to the `dinein` items too) and shorten the disclosure
   in `menu.html` (`.mnote`) and the footer (`_source/partials/bottom.html`).
2. **Hours.** `content/site.json → hours` drives the live open/closed line. The printed
   hours also appear in the JSON-LD in `index.html`, the hero meta, the route facts, the
   visit block and the footer — grep `11:00–21:00`. The 20:30 figure is the LINE MAN
   delivery cut-off, not the kitchen; confirm both.
3. **The lunch set.** The card is the restaurant's own post, undated. If it has ended,
   remove the `lunch` block from `menu.json`, the lunch card from `index.html`
   (`.lunchcard`) and the `#cat-lunch` chip/rail entries are regenerated automatically.
4. **Photographs of the house.** The only owner photograph of the rooms is the small
   Facebook graphic used in "This house". Every exterior and interior view that exists
   online is a reviewer's photograph and was not used. Ask the restaurant for its own
   photographs of the gate, the sign, the bar and the private room; the gallery board and
   the house section have slots waiting (see `GALLERY` in `_source/build.py`).

## Design in one paragraph

Central idea: **the house you have to find**. The restaurant is behind a gate in a
residential soi and reviewers call it ร้านลับ, so the site is the way in — the loader is
the round disc sign switching on, the hero puts you at the gate with the plate in view, the
signature interaction is a hand-drawn route from Prachachuen Road to No. 34 that draws
itself as you scroll and ends on the Directions button, and the language switch is the
gate closing and opening. Bodoni Moda + Trirong (a Didone in both scripts, because the
cuisine is Parma and Paris) with IBM Plex Sans Thai for everything read; colours are
pixel-sampled from the logo, the green plaster wall, the lunch card and the rooms. The
only circle is the disc; everything else is square like the menu-board tiles.

## Accessibility and motion

Semantic landmarks, one `h1` per page, visible focus rings, keyboard-operable menu,
lightbox and mobile panel with focus trapping and restoration, all text at WCAG AA in every
colour room (audited by probe), `prefers-reduced-motion` honoured (no loader, no gate, no
reveals, no drift; the route is drawn), and nothing depends on JavaScript to be readable —
reveals only arm once the script confirms it is running. Thai display line-height never
drops below 1.28; reveal masks carry overscan so tone marks are never clipped.

## Verified by probe (WKWebView harness + real browser)

- No horizontal overflow at 375 / 768 / 1440 on every page (scrollWidth == clientWidth).
- 0 broken images, every `<img>` with alt and dimensions; every menu row's photo bound to
  its own dish slug (33/33); rows without an owner photo of the actual dish show no photo.
- Language: every `data-en` node swaps and restores; `<html lang>`, title, description and
  `alt` follow.
- Lightbox: opens with the right image, locks scroll, arrows and Escape work, focus returns.
- Menu: hover preview never covers name or price and stays on screen; rapid hover leaves no
  stale state; one inline panel open at a time; touch spotlight centres the nearest row.
- Header, route drawing and reveals use timers and IntersectionObserver, not rAF, so they
  also work in background tabs.
- Every external link resolves 200 and lands on this business; the LINE short link
  resolves to the restaurant's official account.
- Single-file build: 5 pages, 42 images, router, lightbox, menu and language all re-probed.
